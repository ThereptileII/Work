# Initial protected B0 admission driver

`test-installed-protected-b0-startup-windows.py` is the missing admission step
before the separate four-phase installed updater driver. It runs only on an
explicitly disposable, interactive GitHub-hosted Windows runner in
`ThereptileII/Work`, as the actual elevated intended client. It performs one
fresh protected `--activate-startup=true` enrollment, then one original B0
launcher startup. It waits for real initial qualification, selected-history
readback, ordinary application startup and normal UI close. It does not build,
approve an input, publish metadata, connect a tailnet, seed a profile, repair,
retry, uninstall, remove fixed objects, or force a process to exit. Never run it
on the boat or a machine with physical equipment connected.

Before running, an operator must independently authenticate the original B0
recovery/source/policy, exact same-commit native operator kit, final provisioner
and its loader/publisher, supported stock OpenCPN, and the original public trust
and signed bootstrap policy. The original client-registration request and its
SHA-256 need a **separate approval after baseline-package production**. Neither
`skager-baseline-package` output, its printed hash, the kit's own checksum
manifest, adjacent files, this driver's declaration, UAC, nor a freshly computed
hash approves that request or first execution. The declaration's SHA-256 and
the separate command-line SHA-256 pins below must come from those independent
approval records. They are not generated by this driver.

The operator also preprovisions and approves the existing protected NTFS
bootstrap cache and acquisition directories. The acquisition directory already
contains the original `approved-installed-baseline.zip` and the approved
trust JSON exists separately. The supported x86 OpenCPN 5.12.4 stock executable
and an initialized current user's `opencpn` profile already exist. That profile
has a nonempty `navobj.xml` and reviewed stable settings in `opencpn.ini`;
equipment and external connections are disabled. The real provisioner checks
the protected input ancestry and creates the fixed service/files exclusively;
the driver does not claim absence from a directory scan. An existing or partial
protected namespace refuses and remains for review.

Create a B0-only declaration as an original approved file. Paths are absolute
ordinary files or existing directories without reparse ancestors. `b0` is the
same record form used by the four-phase driver, with the genuine original
product version and compiled 40-hex commit:

```json
{
  "schema": 1,
  "b0": {
    "version": "<genuine B0 version>",
    "commit": "<B0 compiled 40-hex commit>",
    "recovery": {"path": "C:\\approved\\b0-recovery.zip", "sha256": "<approved SHA-256>"},
    "source": {"path": "C:\\approved\\b0-source.zip", "sha256": "<approved SHA-256>"},
    "policy": {"path": "C:\\approved\\b0-beta.json", "sha256": "<approved SHA-256>"}
  },
  "operatorKit": {"path": "C:\\approved\\b0-operator-kit.zip", "sha256": "<approved SHA-256>"},
  "clientRequest": {"path": "C:\\approved\\original-client-request.json", "sha256": "<separately approved request SHA-256>"},
  "brokerBootstrapPolicy": {"path": "C:\\approved\\original-broker-beta.json", "sha256": "<approved signed-target bytes SHA-256>"},
  "approvedBaseline": {"path": "C:\\ProtectedAcquisition\\approved-installed-baseline.zip", "sha256": "<approved original recovery ZIP SHA-256>"},
  "trustConfig": {"path": "C:\\approved\\update-trust.json", "sha256": "<approved public trust SHA-256>"},
  "bootstrapCache": "C:\\ProtectedCache",
  "artifactDirectory": "C:\\ProtectedAcquisition",
  "preserveSettings": [{"section": "Settings", "key": "<reviewed existing stable key>"}]

```

The bootstrap policy pin is for the distinct signed
`bootstrap/broker-beta.json` target, not `releases/beta.json`. Publish the
original B0 beta policy and obtain its independently approved timestamp SHA-256
before this invocation. The selected private HTTPS endpoint and hosted runner's
tailnet access are separate external prerequisites. The driver uses the existing
read-only publication observer before and after the operation; the real broker
still performs signature, expiry and rollback-floor verification.

```powershell
python tools/test-installed-protected-b0-startup-windows.py `
  --declaration C:\approved\b0-admission.json `
  --declaration-sha256 <independently-approved-declaration-sha256> `
  --approved-client-request-sha256 <separately-approved-original-request-sha256> `
  --approved-bootstrap-policy-sha256 <independently-approved-broker-bootstrap-policy-sha256> `
  --approved-provisioner-sha256 <independently-approved-final-provisioner-sha256> `
  --approved-broker-sha256 <independently-approved-native-broker-sha256> `
  --timestamp-sha256 <independently-approved-B0-publication-timestamp-sha256> `
  --evidence C:\acceptance\first-b0 `
  --disposable-opt-in SCRUM-311-disposable-initial-protected-b0
```

The verified kit is copied into a fresh, retained child of the independently
protected acquisition directory. The final provisioner image is held against
write/delete and rehashed before its single elevated invocation. The command
passes only the original independently pinned trust, cache, artifacts, bootstrap
policy, provisioner, and client request to the existing native CLI. It never
derives approval from the kit manifest. Any timeout leaves the original process
alive and the fixed namespace untouched. A failed or ambiguous result stops the
driver; it never starts a second enrollment or attempts cleanup.

On enrollment success, the driver launches only the original installed B0
`skager-start.exe --broker-start=<approved generation>` through the existing
native phase observer. It requires actual selected-history B0 version, commit,
generation, completion, qualification, clean qualification-close and inventory
hashes, with no pending state or ancestor. It checks nonempty navigation and
approved setting hashes before enrollment and after normal application close.
`result.json` is created only in a fresh evidence directory; staged operator
files and evidence are retained on refusal. A successful result means only this
initial native B0 admission and scoped preservation passed. It does not qualify
the later B1 update phases, ordinary unelevated users, historical Setup,
repair/uninstall, full product acceptance, or hardware/boat use. The component
producer commit and this helper revision remain distinct evidence.

Portable inert checks: `python tools/test-installed-protected-b0-startup-windows-tests.py -v`.
Actual Windows admission remains a separate native gate.
