# Secure startup update verifier (SCRUM-25)

The original verify-only probe below is historical evidence. Current code adds
protected persistent trust, verified artifact custody, explicit native startup
consent and transactional installed-generation recovery. See the current
[secure updater contract](../../docs/installer/secure-updater.md). The pinned
dependency graph and original probe results do not by themselves qualify this
integrated updater. No production trust root or update endpoint is provisioned.

## Original probe evidence

This is an isolated, verify-only feasibility probe. It does not provision a production root, name a production endpoint, select an installer, download an executable package, or integrate with the current installer. `Verify` requires a caller-provided trusted root and durable protected metadata cache, refreshes all top-level TUF metadata, checks the selected channel's target, and returns only verified bytes plus version and commit from signed target metadata. The placeholder Go module path denotes this boundary.

The repository uses `github.com/theupdateframework/go-tuf/v2` **v2.4.2**, tag commit `f5edbde31e5507f46db2069402dc38903fe6d9d4` ([source](https://github.com/theupdateframework/go-tuf/tree/v2.4.2), [Apache-2.0 license](https://github.com/theupdateframework/go-tuf/blob/v2.4.2/LICENSE)). `go.mod` and `go.sum` pin and checksum module dependencies. `go list -m all` resolves 83 modules including the probe; 259 packages are in the local library build graph. The non-test package graph includes `sigstore/sigstore` through TUF metadata imports; it is not only a fixture dependency. The inspected Linux/amd64 and Windows/386 runtime graphs contain the same 12 third-party modules. This remains a material dependency and notice-review cost before product adoption. The Windows 386 test executable built on Linux is 18,644,480 bytes; this is a **test binary**, not an estimated shipping size. `go.mod` records the complete direct and selected transitive module versions; run `go list -m all` for the entire graph and review each transitive license before distribution.

Local validation used official Go 1.27.1 in ignored `.local/`, with the official Linux archive SHA-256 `63d339f0da5ab53635a56f2490a7984dfe12dfcff22ad749f63edaf590168445`. Run from this directory: `go test ./...`, `go vet ./...`, and `GOOS=windows GOARCH=386 go test -c -o <ignored-output> .`. Exact probe commit `24bd013f4891638f0e59411836c67f271a66a645` passes the dedicated Linux and native Windows/386 workflow in [run 36936782032](https://github.com/ThereptileII/Work/actions/runs/36936782032). Downloaded JSON results pass six top-level tests and nine subtests on each platform. Cross compilation alone does not qualify Windows behavior; these results do not qualify a later policy implementation or installed updater.

Tests create fresh Ed25519 keys and all four signed top-level roles in memory. They cover valid bytes, same-size SHA-256 tampering, length mismatch, malformed or invalidly signed metadata, expired timestamp, timestamp rollback after trusting a newer version, absent stable target, signed wrong channel/invalid commit, metadata and target size limits, total deadline, and cross-origin redirect. The test TLS server is a local fixture. Production requests require HTTPS on one origin, normal TLS validation, 15-second request timeout, 30-second shared operation deadline, bounded metadata and target lengths, and no redirects to another origin. These are spike defaults, not approved deployment policy.

Remaining acceptance gates: securely provision and rotate a pinned root; protect and recover the durable cache; specify threshold keys and repository operations; sign a real per-channel release policy; enforce application version anti-downgrade using trusted installed-version state; review every dependency license and Windows binary size; qualify the integrated updater on native Windows; and design installer handoff/rollback. TUF metadata rollback protection alone does not prevent correctly signed metadata from advertising an older application version. No production update path should use this probe yet.

`VerifyArtifact(reader, artifact)` checks a caller-supplied stream against the positive length (at most 4 GiB) and lowercase SHA-256 in an **already authenticated and parsed release policy**. It uses a fixed buffer, reads at most the declared length plus one byte, rejects truncated/extra/tampered bytes and reader errors, and stops repeated zero-progress reads. It does not open files, access the network, execute or install anything. Callers must bound blocking reads and retain the same verified bytes for any later execution: this helper does not establish file custody or prevent replacement between verification and use. Payload integrity alone does not authorize an update or replace compatibility, anti-downgrade and installer gates.
