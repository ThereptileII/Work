# TUF update verification spike (SCRUM-25)

This is an isolated, verify-only feasibility probe. It does not provision a production root, name a production endpoint, select an installer, download an executable package, or integrate with the current installer. `Verify` requires a caller-provided trusted root and durable protected metadata cache, refreshes all top-level TUF metadata, checks the selected channel's target, and returns only verified bytes plus version and commit from signed target metadata. The placeholder Go module path denotes this boundary.

The repository uses `github.com/theupdateframework/go-tuf/v2` **v2.4.2**, tag commit `f5edbde31e5507f46db2069402dc38903fe6d9d4` ([source](https://github.com/theupdateframework/go-tuf/tree/v2.4.2), [Apache-2.0 license](https://github.com/theupdateframework/go-tuf/blob/v2.4.2/LICENSE)). `go.mod` and `go.sum` pin and checksum module dependencies. `go list -m all` resolves 83 modules including the probe; 259 packages are in the local library build graph. The test signing helper brings in `sigstore/sigstore`; this is a material dependency and license review cost before product adoption. The Windows 386 test executable built on Linux is 18,644,480 bytes; this is a **test binary**, not an estimated shipping size. `go.mod` records the complete direct and selected transitive module versions; run `go list -m all` for the entire graph and review each transitive license before distribution.

Local validation used official Go 1.27.1 in ignored `.local/`, with the official Linux archive SHA-256 `63d339f0da5ab53635a56f2490a7984dfe12dfcff22ad749f63edaf590168445`. Run from this directory: `go test ./...`, `go vet ./...`, and `GOOS=windows GOARCH=386 go test -c -o <ignored-output> .`. The dedicated workflow runs the tests as native Windows 386 processes on a Windows host when this branch is submitted. Cross compilation alone does not qualify Windows behavior.

Tests create fresh Ed25519 keys and all four signed top-level roles in memory. They cover valid bytes, same-size SHA-256 tampering, length mismatch, malformed or invalidly signed metadata, expired timestamp, timestamp rollback after trusting a newer version, absent stable target, signed wrong channel/invalid commit, metadata and target size limits, total deadline, and cross-origin redirect. The test TLS server is a local fixture. Production requests require HTTPS on one origin, normal TLS validation, 15-second request timeout, 30-second shared operation deadline, bounded metadata and target lengths, and no redirects to another origin. These are spike defaults, not approved deployment policy.

Remaining acceptance gates: securely provision and rotate a pinned root; protect and recover the durable cache; specify threshold keys and repository operations; sign a real per-channel release policy; enforce application version anti-downgrade using trusted installed-version state; review every dependency license and Windows binary size; run native Windows tests; and design installer handoff/rollback. TUF metadata rollback protection alone does not prevent correctly signed metadata from advertising an older application version. No production update path should use this probe yet.
