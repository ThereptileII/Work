# Public-beta web and commerce architecture

Status: selected technical direction for SCRUM-31. This document describes the required design; it does not claim these services are implemented or deployed. This decision does not approve vendor accounts, spending, deployment, public payments, or public downloads. Customer-facing identity is **SKAGER / SKAGER App** and `skager.app` is the selected domain; domain control and legal clearance remain launch gates. The existing OpenCPN application and plugin remain native software with the established Windows ABI.

## Decision

Build a server-rendered **Django 5.2 LTS modular monolith** backed by PostgreSQL. Deploy the web process and a separate worker in Render's Frankfurt region. Use Auth0 Universal Login over OpenID Connect (OIDC), Paddle as Merchant of Record (MoR), private object storage for uploads and release binaries, and the existing Jira project through a server-only adapter.

Django owns marketing pages, portal views, authorization, orders, entitlements, release metadata, support intake and operational administration. Modules share one database but have explicit service boundaries: `accounts`, `orders`, `webhook_inbox`, `entitlements`, `releases`, `support`, `jira_outbox`, `uploads`, and `audit`. Cross-module state changes run in database transactions; slow or remote effects enter an outbox for the worker. Versioned migrations and pinned dependency versions selected and recorded during implementation make upgrades reviewable. Django 5.2 LTS receives security and data-loss fixes until April 2028 ([support table](https://www.djangoproject.com/download/)).

This shape is small-team maintainable: one deployable codebase and database, few network trust boundaries, server-rendered accessibility and SEO, and no duplicate browser API/application state layer. A single-page application would add token handling, CORS, API versioning and two release surfaces without a current product need.

## Identity and session boundary

Auth0 hosts signup, login, recovery and account authentication. The server uses the OIDC Authorization Code Flow ([Auth0 flow](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow/add-login-auth-code-flow)). It validates issuer, audience, signature, nonce and state, and identifies an account only by the immutable `(iss, sub)` pair. OIDC login does not prove a person's legal identity. Email is display/contact data and never joins purchases or identities by itself.

After callback, Django creates its own short-lived, rotated session in a `Secure`, `HttpOnly`, `SameSite=Lax` cookie. State-changing requests require CSRF protection; authorization is rechecked server-side for every portal object, download and support action. The browser receives neither Auth0 management credentials nor Paddle, Jira, database, signing or object-storage secrets. Auth0 currently advertises a Free tier up to 25,000 monthly active users and Essentials from USD 35/month at 500 MAU ([pricing](https://auth0.com/pricing/)); production feature eligibility, custom-domain needs and final tier must be verified before purchase.

Running passwords locally with django-allauth would reduce vendor dependence but would make this team responsible for password storage, recovery abuse controls, MFA and identity operations. It remains a fallback only if Auth0 cannot meet production, privacy or cost requirements.

## Commerce and entitlement flow

Paddle is selected as MoR for the USD 20 one-time Public Beta Access product. It acts as reseller and handles payment processing, sales-tax/VAT calculation, collection and remittance for supported transactions; legal review must still confirm SKAGER's own accounting, income-tax, invoicing, terms, refund and jurisdiction duties. Vendor onboarding, product approval, country coverage, payout terms and the final refund policy are unresolved launch gates, not assumed capabilities.

Paddle supports one-time digital products ([product model](https://developer.paddle.com/get-started/how-paddle-works/digital-products/)) and lists pay-as-you-go pricing of 5% + USD 0.50 per checkout transaction ([pricing](https://www.paddle.com/pricing)). On USD 20 that is a USD 1.50 base processing fee before tax effects; it is not a net-profit estimate. Discounts use provider-managed discount codes ([discounts](https://developer.paddle.com/build/products/offer-discounts-promotions-coupons/)). Lemon Squeezy is the MoR fallback: its [published pricing](https://www.lemonsqueezy.com/pricing) has the same base rate plus possible international or PayPal fees; vendor approval and final commercial fit must be evaluated.

The purchase sequence is:

1. An authenticated account asks Django to create a pending local order. The server binds that order to the account, approved product, price/currency and environment, creates the provider transaction itself, and stores the immutable local-order/provider-transaction mapping. No card data reaches SKAGER.
2. Browser success or cancel redirects are presentation only. They never grant entitlement.
3. The webhook endpoint reads a bounded raw body, verifies Paddle's timestamp and HMAC signature before parsing ([verification](https://developer.paddle.com/webhooks/about/signature-verification/)), rejects stale/replayed invalid input, then persists the provider event ID, payload digest, relevant normalized data and receipt time before acknowledging it.
4. A worker claims the inbox row and verifies the expected vendor account and environment, immutable transaction mapping, approved product, currency, price or authorized discounted total, and completed-payment status. Correlation/custom data, email and redirect state are never sufficient to grant access.
5. The worker applies a verified event once, records its payment effect and audit event, and advances order/entitlement state monotonically. Paddle documents at-least-once delivery, retries and non-guaranteed ordering ([delivery](https://developer.paddle.com/webhooks/about/how-webhooks-work/)); unique event IDs, row locks and state/version checks prevent duplicates or older paid events from undoing a later refund or reversal.
6. A scheduled reconciliation job compares local orders/refunds with provider state and raises discrepancies for human review.

Completed payment creates an active server-side entitlement. A full refund moves it to refunded and ends future hosted access; partial refunds require an explicitly approved policy before implementation. Chargebacks and reversals suspend hosted access pending review, and their terminal sequence/version guard prevents a delayed paid event from resurrecting access. Refund behavior must be tested in the provider sandbox and staging, including duplicate and out-of-order events. Installed GPL-covered native software remains usable offline; hosted entitlement changes neither revoke that software nor retract GPL rights or source already received.

## Releases, support and data

`releases` maps one immutable application commit to binary, checksum, manifest, signature, release notes, license notices and corresponding-source objects. Every release has a public, version-specific corresponding-source and legal path with no entitlement gate. Private official binaries use short-lived, single-purpose signed download URLs after server-side entitlement checks. Update authorization uses the same release and entitlement service.

Release signing is separate from the web host: an offline or protected CI key signs manifests and artifacts; the web service stores only signed results and public verification material. The native updater verifies the signature plus expected channel/version, manifest expiry and rollback policy. A web compromise cannot sign a new trusted binary, but client checks are still required to reject replayed, expired or downgraded signed material.

Support submissions validate type, size and content. Uploads land in a private quarantine bucket under random object keys, are malware/content scanned, and become accessible only through bounded, audited server-mediated links. The Jira adapter holds service credentials privately. `jira_outbox` records sanitized issue creation/update commands and retry state; portal users see only an allow-listed customer status and their own submitted fields. Internal comments, Jira identifiers where inappropriate, unrelated issues and credentials never cross the customer boundary. Existing Jira issue links express implementation ownership; this document creates no private backlog.

Core records retain Auth0 subject, minimal contact profile, provider customer/order/transaction references, entitlement history, release access audit, support content, upload metadata and security/operations logs. Retention periods must be approved in the privacy policy and enforced by jobs. Export produces the customer's stored data; deletion removes or anonymizes eligible identity/support data while preserving narrowly required financial and security records with documented legal basis. EU application and database hosting alone does not establish data residency: Auth0, Paddle, object storage, email, logging, support processors and cross-border transfers must be assessed together.

## Environments, operations and cost

Development, staging and production have separate Auth0 tenants/applications, Paddle sandbox/live credentials, databases, object-storage namespaces, Jira integration identities and secrets. Staging uses synthetic accounts and provider test payments. Production secrets live in protected environment configuration; TLS terminates at the platform, and security headers, rate limits, audit logging and alerting are application requirements.

Render offers Frankfurt services ([regions](https://render.com/docs/regions)). Its published entry prices are USD 7/month for a 512 MB web service and USD 6/month for 256 MB Postgres; database storage is USD 0.30/GB-month ([pricing](https://render.com/pricing)). Thus one web service plus 1 GB database storage starts at USD 13.30/month. This is a price reference, not a capacity qualification. Production also needs a worker, and two hosted environments multiply applicable services. Object storage/egress, transactional email, domain/DNS, Auth0 tier, monitoring/log retention, backup tier, tax/accounting, overages and support are additional unknowns to quote before approval; none is treated as zero.

Each environment has automated database backups and a documented restore procedure. Render's paid Postgres point-in-time recovery window is currently three days on Hobby and seven days on Pro ([backups](https://render.com/docs/postgresql-backups)). Launch requires a timed restore rehearsal into an isolated database, integrity checks for orders/entitlements/releases, and recorded recovery evidence. Deployment uses reviewed migrations, health checks, backward-compatible rollout where needed and rollback to the preceding application image; destructive migrations require a tested recovery path.
