# Terminal protected service decommission

SCRUM-27's bounded service-only transaction preserves every application, profile,
shortcut, registration, journal, backup and trust-floor object. It is not full
uninstall, shortcut restoration or repair. Source joins and native installed
acceptance remain required before use.

An independently authenticated elevated operator opens the original running
broker service, approved installed image and exact original client request before
requesting `prepare-decommission` through the fixed authenticated maintenance
pipe. The caller supplies only a fresh request ID and expected selected-head hash.
The broker retains its operation/store locks, actual elevated registered peer,
current selected-chain readers, SAME exited ordinary-application owner, frozen
CURRENT profile, original stock executable and legacy armed-marker denial. A
missing application owner after service restart is not proof of exit.

The actual machine service is shared. All protected registration-root entries
must be bounded, exact, complete and owned by the one registered client; foreign,
unknown, aliased or partial evidence refuses. Actual completed generation,
launch-parent, execution, stage and profile-backup evidence must be validated and
retained through their existing readers. A two-file registration-only fixture
cannot qualify a real installed selected generation.

The original Store makes one CREATE_NEW attempt for a permanent terminal marker,
binding request/client, registration, selected generation/completion/head and
current profile content/identity hashes. Flush and exact original readback are
mandatory. Any marker presence or lookup uncertainty permanently refuses ordinary
store use and service startup, including malformed or incomplete marker bytes.
There is no marker deletion, adoption, retry, re-enrollment or floor reset.
Post-publication checks use only the original sealed receipt and independently
retained native owners; ordinary store/history checks intentionally deny access.
Any dedicated terminal drain must preserve actual original-reader poison and
handle-close errors rather than weakening ordinary validation.

Only the authenticated native response can construct the opaque
`DecommissionWitness`. It retains the SAME original broker's service, process,
token and image custody, request binding and creation time. Neither response JSON,
a PID lookup, a copied/zero witness nor an administrator declaration grants this
capability. The independently retained service owner must match the witness before
any SCM effect. A temporary folder-query token grant follows the existing scoped
maintenance rules and must be restored; cleanup uncertainty refuses success.

The explicit `decommission-service` operator action then disables the SAME retained
SCM service, reads back its exact disabled configuration, dispatches one STOP and
proves original process zero exit, then calls DeleteService on that same retained
handle. Only this distinct owner mode requests CHANGE_CONFIG/DELETE rights;
ordinary maintenance remains query/STOP only. Unexpected restarts, cancellation
or uncertain effects revoke the owner. No application/profile/file effect follows
shutdown. All original native owners must close before emitting successful data.

Success reports only `marked-for-removal`: DeleteService is not proof that SCM
absence has already occurred. A separate read-only absence observation may be
recorded later; it cannot authorize cleanup. The separately installed stock
OpenCPN executable remains unchanged. SKAGER-owned files/shortcuts are retained
for recovery and this slice does not claim they are usable after service removal.
A later full uninstall must safely restore/remove its own objects under separately
qualified original ownership and lifecycle authority.


## Explicit protected application retirement

The separate elevated `--maintenance=uninstall-protected` action uses the same
original broker/client/request/head inputs and additionally **requires** both
original completed startup-publication options documented in
[original startup restoration](operator-startup-decommission.md). Omission is
not evidence that shortcuts were never activated and refuses before input reads.
No new approval record or serialized custody object is introduced. This action
restores original owned shortcuts, drains original descendant readers, retires
the selected protected application generation and its completed registration pair
into fixed protected recovery names, then disables/stops/marks the same original
service for removal. The revised ordering passes the focused native Win32
component gate at `d7be409d`,
[run 38512820510](https://github.com/ThereptileII/Work/actions/runs/38512820510).
Ordinary Setup/Lifecycle uninstall and installed-product qualification remain
separate integration gates. Its protected-enrollment observation intentionally
refuses any retained protected namespace, including this terminal recovery. Do
not call the old Lifecycle uninstall or bypass its guard using this CLI result;
a bounded authenticated terminal-cleanup handoff is still required.

The fixed authenticated pipe uses the distinct `prepare-uninstall` operation.
While the selected owner still validates, `PrepareRetiringDecommissionLineage` retains
its original physical identities and protected parents. The host requires a clean
selected-generation/journal-reader close. Commit then acquires matching DELETE
owners **before** creating the terminal fence. Fixed recovery destinations must
be absent, and every move is non-replacing. The native retirement journal precedes
the first move. No post-fence open, path scan, retry or replacement grants custody.
The current profile, stock OpenCPN and unknown objects are preserved.

`CommitWithStartupDrain` holds original retirement custody across a synchronous
callback after the terminal marker and durable started record, before any move.
The host sends a single sealed intermediate `uninstall-fenced` response with an
empty retirement hash. Within the same bounded pipe conversation the original
operator restores shortcuts and drains app/launcher descendant handles, then
acknowledges that exact request and fence. The host rechecks standalone
operator/profile/stock/application custody and the store checks its original
terminal owners before continuing. No ordinary Store checks, fresh endpoint,
second preparation, reconnect or serialized intermediate receipt can resume it.
The borrowed intermediate capability is revoked when its callback returns and
never permits SCM disable/STOP/removal. The protected operator action has one
90-second deadline spanning original preparation, the pipe exchange and final SCM
effects; the intermediate restoration exchange is additionally bounded to
30 seconds. Expiry cannot mint a final witness or restart the operation.
Native Windows rejects directory rename
with open descendant handles even when they share deletion; the original failed
run [38465784927](https://github.com/ThereptileII/Work/actions/runs/38465784927)
is preserved rather than reclassified as a fixture failure.

Only completed native retirement returns `uninstall-prepared`, including mandatory
`retirementSha256` as well as the existing fence/binding fields. The sealed live
broker witness binds this distinct response; fence-only service decommission
cannot satisfy it. The provisioner binds that witness to the original retained
SCM owner, requires the completed original shortcut restoration/drain, and completes service
removal before closing all owners. Its result state is
`protected-retired-service-decommissioned`, with `service` equal to
`marked-for-removal` and `startup` equal to `original-shortcuts-restored`.
This does not assert immediate SCM absence or removal of the ordinary product
wrapper, older recovery generations, histories, journals or trust floors.

Cancellation, changed identity, failed owner close, collision, partial move or
lost response returns no successful result and never dispatches a second action.
Preserve the terminal fence, retirement records and every original/recovery object
for explicit operator recovery. Do not rerun with a new request ID, clean partial
state, recreate registration or reset trust. Native Windows/MSVC and an actual
installed end-to-end transaction with exact candidate bytes are still required;
portable protocol/ordering faults and cross-compilation cannot grant acceptance.

## Closed updated lineage and original startup identity

The host now derives retirement comparisons from every retained original
execution journal, after the existing selection reducer has proved a closed,
nonforking history and exactly the same selected head/completion/version.
Pending or unexecuted staged candidates are not inferred qualified. The list is
baseline first, with remaining distinct generation IDs sorted deterministically;
the selected generation need only be a member. Consequently completed automatic
or manual rollback can select B0 while B1 still requires retirement. Resolved
no-spawn candidates also remain in the exact comparison set. Conflicting
completion hashes for one generation refuse.

The native Store independently requires the completed generation namespace to
equal that set. It checks original approved-baseline and signed-candidate
purposes, original completion bytes, completed stage seals, parent identities
and every retained root. Extra, pending, partial or changed objects refuse.
Schema-2 started/completed records bind the explicit baseline and all ordered
generation/purpose/completion/root identities. Registration and all generation
DELETE handles remain held across the same startup-drain callback; every move
uses its original handle and fixed non-replacing retirement name. Unknown
children move with their original root and are preserved. The existing
baseline-only adapter retains schema 1 for its bounded callers.

Original startup publication still owns B0's original launcher and root, even
when the sealed interim/final result reports selected B1. The operator binds the
same original B0 root at `retired-<request>-<B0>`; it neither substitutes B1 nor
reopens drained descendants. Exact interim/final conversation matching remains
mandatory. These component changes do not make the old Lifecycle uninstall safe
to run or qualify the installed maintenance UI.

Installed teardown also needs to avoid restoring a link whose target is then
removed. Its startup boundary classifies the already-held original shortcut
before fencing, using the Windows system ShellLink implementation with an
in-memory stream. It never resolves or executes a link, consults mutable COM
registration, or opens a target path. Malformed/truncated fields refuse.
Only an exact authenticated integration-target comparison permits retirement;
stock and unknown targets are preserved. After final witness binding, while
that witness is still live, the same original link handle moves non-replacing
to `retired-original-Skager.lnk` in the already-held recovery directory. Its
bytes and identity stay retained through SCM shutdown. This is a private join
for installed teardown, not a callable receipt-based cleanup mechanism.
