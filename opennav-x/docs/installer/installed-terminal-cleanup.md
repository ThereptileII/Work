# Installed terminal cleanup ownership

SCRUM-27. This source contract extends the explicit protected retirement path
and its fixed customer entry. It is not acceptance of full installed uninstall,
maintenance UI, repair, package delivery or boat operation. Native component
checks and actual installed qualification remain separate.

## Original installation and customer maintenance

The independently authenticated original enrollment transaction now installs
its exact signed-bootstrap provisioner bytes beside the fixed broker under
ProgramFilesX86/SKAGER/UpdateBroker. Source and destination stay under original
native custody. The helper's PE32 loader accepts the expected system-only Go
import contract; it does not establish its own first-execution trust.

After original client/baseline registration and shortcut publication, that same
transaction reserves `<SID>.maintenance.once` in the existing protected
ClientRegistrationRequests directory. Only its original retained publisher may
commit `<SID>.maintenance.json`. It binds the exact original request/publication
bytes, original directory/file identities, baseline, broker and maintenance
helper. The completion marker is committed only after durable original-handle
readback and rechecking the same running service. Interrupted/partial or existing
state is preserved and refused, never adopted or repaired automatically.

This is original installation authority retained against ordinary users.
Admin/SYSTEM remain trusted machine principals, as explicitly defined by
`createFreshFiles`; a vendor countersignature for per-install shortcut IDs is
not required. An adjacent file supplied by the application is not equivalent.

The customer action `--maintenance=uninstall-current` takes no approval hashes,
input directories, SID or cleanup paths. Its native owner derives the actual
current user, reads the fixed protected completion and marker, retains all
original objects, verifies the actual fixed running helper, and joins the
existing live broker flow. Missing original completion in older installations
requires the separately approved operator recovery path. Current ACLs alone
cannot migrate or approve such an installation.

Read-only `InspectRetainedApprovedBaseline` verifies the original archive and
returns owned member metadata after bootstrap expiry. It cannot write, install,
reset trust or grant cleanup permission. Only the private native completed-owner
path uses it for maintenance. Fresh enrollment and the public operator importer
retain their current-clock trust checks. Current broker history/floors and the
sealed terminal conversation still govern every effect.

The user-level maintenance wizard delegates protected Uninstall to the fixed
native helper. The helper owns the same-account elevation check and waits for
the exact child result. Neither cancellation nor failure may fall back to the
old Lifecycle cleanup. Repair and rollback retain their separate current gates.

The unelevated helper retains its original process and fixed protected code.
Windows owns the UAC prompt; the elevated child verifies the original live
parent's SID, session, creation time and fixed image. Different-account elevation
refuses instead of selecting an administrator's profile. A bounded 105-second
handoff contains the 90-second maintenance operation. Parent loss cancels the
operation; a late prompt cannot authorize cleanup after the original parent
exits. No forced termination or automatic retry is used. Completion output waits
for the parent monitor, native checks and all original owner closes. Actual UAC
and complete installed wizard execution remain separate native acceptance gates.

## Explicit operator path and terminal effects

`--maintenance=uninstall-installed` requires the independently approved original
client request, original startup publication and original baseline artifact.
The same `MaintenanceOwner` prepares startup and installed custody before asking
its one live broker to fence, restore/drain startup descendants, and retire the
closed completed generation lineage. An updated or rolled-back selected head
must remain in that lineage; pending or ambiguous history refuses. The original
startup anchor always belongs to the original approved baseline.

The installed owner resolves the approved user's actual LocalAppData, fixed
`OpenNavXAlpha1` integration root, exclusive existing transaction lock and fixed
Programs/SKAGER menu. Mutable state may locate only a bounded generation below
that root. It cannot authorize cleanup paths or hashes. The retained original
approved ZIP independently supplies exact installed member sizes/hashes and a
closed installer-helper copy mapping. Original matching members receive native
read/DELETE custody before any terminal broker effects. Missing members are
already absent; changed, unknown or unapproved members remain. Recovery and
stock OpenCPN remain retained and are never recursively removed. No profile,
chart, route, plugin, connection or other navigation data is a cleanup target.

During startup restoration, a stock or unknown original normal shortcut remains.
An original link pointing exactly to the verified integration may instead be
retired, using its original handle, into the fixed original startup recovery
folder. Fixed Legacy and maintenance menu links require exact target, arguments
and working-directory matches. The maintenance link's target is a narrowly
recognized current-generation `Maintain.exe`; retiring that link does not grant
permission to remove that executable or its payload. Arbitrary link targets are
never launched or followed.

Only a matching final native broker witness permits integration-link retirement,
service disable and STOP. After the original broker process exits successfully,
cleanup rechecks the same retained file, startup, stock and service owners. It
must not reuse the now-expired live process witness as a post-exit check. Verified
members are marked for deletion through their original handles. Original
`state.json` moves without replacement to `retired-state.json`; a replacement
active state or colliding retired name refuses. Recovery bytes remain.

The fixed approved-SID Windows uninstall registration uses an original retained
HKEY plus an explicitly bounded registry transaction. Preparation checks the
exact eight expected values, no subkeys, the original security boundary and
32-bit registry view. Staged deletion uses the same original transacted key;
there is no pathname-delete or nontransactional fallback. Commit is allowed only
after exact revalidation. Conflict, timeout, unsupported API, cancellation or
partial failure preserves uncertainty and forbids retry or fallback. Native
fixtures must establish actual visibility, rollback and conflict semantics;
Linux mocks and cross-compilation cannot establish those Windows properties.

Service deletion marking follows successful installed cleanup. The CLI reports
success only after closing original owners and the borrowed witness, with the
bounded operation context still valid. Its JSON is a final observation, never
cleanup authority for a second process. The old PowerShell Lifecycle protected
root refusal remains in place. The fixed customer path reuses these same native
owners instead of handing result JSON back to Lifecycle. Neither path qualifies
an actual installed B0/update/rollback/uninstall journey merely by passing
component tests. Interrupted terminal work requires explicit recovery, never
blind retry.
