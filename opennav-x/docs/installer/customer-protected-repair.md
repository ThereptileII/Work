# Protected customer Repair

Maintain **Repair** invokes only the fixed installed
`skager-update-provisioner.exe --maintenance=repair-current`. The original
unelevated process retains the real same-account/session UAC child. No customer
argument supplies a SID, package, source/destination, target, trust configuration
or approval hash. A partial protected namespace refuses rather than entering
legacy Lifecycle.

This increment requires fresh matching broker/helper enrollment. Older brokers
reject the additive `repair-inspect` / `repair-current` operations before mutation;
older helpers reject the action. Application B1 does **not** replace the fixed B0
broker/helper. No broker replacement, migration or re-enrollment is implemented.
The existing-installation upgrade remains a separate design/native blocker.

The customer closes SKAGER, chooses Repair, accepts actual same-account UAC and
confirms the displayed selected version/build. The broker retains its original
ordinary application process/token owner to prove that exact selected generation
exited, alongside the actual elevated operator, original stock owner, armed-state
barrier and CURRENT frozen profile. Missing application custody after SCM restart
refuses; a PID scan cannot replace that owner. Repair stops no process/control.

## Exact restoration authority

Successful acquisition already deleted Recovery ZIP/Setup files. Repair uses the
complete retained private source closure authenticated at original creation:
protected completion/marker, registration/baseline lineage, original source full
file/directory IDs, every member length/hash, and (for signed candidates) original
stage seal/receipt. B0 uses its private initial baseline, never mutable
LocalAppData. Code/package/executable/product/inventory identity stays exact;
network metadata cannot change this same-version operation or reset trust floors.

A dedicated metadata/source reader can inspect missing/corrupt public payload
members. Ordinary public generation reopening still requires the complete
payload and hashes/IDs. Original public roots/parents, completion pair, retained
private source/provenance and original B0 `app/skager-start.exe` must survive.
Entire-root replacement/deletion, missing private authority, invalid ownership or
a damaged original bootstrap launcher refuses. These cases are not advertised as
repairable.

Repair creates a fresh protected generation with identical code and new
physical destination IDs. The damaged root and all its custom additions remain
untouched. Distinct `repaired-generation` provenance binds the original nonrepair
source, current selected predecessor completion and selected head. Repeated
repairs reference the original source directly, never a chain of repaired copies.

A distinct `repair-selected` history edge references a reachable original real
healthy-and-closed source qualification. Repair never launches, restores an old
profile, authors new health/closed facts or claims restored code is freshly
healthy with today's profile. It compares the same frozen current profile and
performs fresh full selected readback. The helper repeats that readback and only
reports completion after retained owners drain successfully. Failure, timeout or
lost reply preserves state and reports uncertainty. A completed copy without
its committed repair journal blocks startup and a later repair attempt; it is
never treated as a reusable staged Upgrade. No automatic retry, cleanup,
rollback or re-enrollment occurs.

## Existing consumers

* Current/Legacy/Safe/offline startup fully verifies restored selected code and
  retains existing current-start authorization, armed/profile, peer/executor and
  prelaunch guards. With nonempty history, bootstrap admission checks only the
  intact original B0 launcher against original physical ID/hash, then requires
  complete selected history before relay. Empty-history qualification still
  validates all original B0 code and requires real qualification.
* History explicitly reports `repairSourceQualification`. The restored
  generation has no ordinary `qualificationSha256` or
  `qualificationClosedSha256`. Older clients that do not understand this
  additive result refuse rather than infer health.
* Strictly newer signed Upgrade can use repaired code as its predecessor.
  Failed-update fallback still needs actual close, profile restoration and
  fallback-health facts; Repair grants none of them.
* Customer Rollback from repaired B1 follows actual head linkage to original
  qualified B0, skipping same-release repair replicas. A historical repair is not
  an independently qualified rollback target: if it is the previous different
  release, customer Rollback refuses. Original qualified manual targets retain
  strict complete payload validation, including refusal if damaged.
* Uninstall's exact closed retirement lineage includes damaged and repaired
  roots. Native retirement verifies the repair's original source completion and
  predecessor membership, with no fabricated same-ID stage seal. Existing
  whole-root retirement preserves unknown public additions. Repair releases the
  consumed old ordinary-process owner; later Uninstall/Rollback requires one
  normal restored-generation start and exit to establish that generation's
  original process custody, as with existing maintenance gates.
